# 선택한 여행지의 일정 생성과 OpenAI 사용 제한

## 연동 범위

사용자가 첫 단계에서 여행지 한 곳을 정한다. 마지막 요약에서 생성을 요청하면 기존 `POST /api/generations`가 여행지, 날짜(1~7일), 동행·인원, 취향과 밀도를 받아 해당 여행지의 일자별 일정을 만든다.

Python 패키지 `openai-agents`는 사용자가 백엔드에 설치한다. 프런트엔드는 Tripick API만 호출한다. `OPENAI_API_KEY`는 서버 환경변수로 주입하고 브라우저 번들, 응답, 로그에서 제외한다. 운영에서는 프롬프트와 응답 본문을 SDK 추적에 남기지 않는다. [공식 Quickstart](https://openai.github.io/openai-agents-python/quickstart/)

생성 API는 로그인·CSRF·저장 슬롯·재생성 소유권 및 버전을 검사하고 작업을 접수한다. 에이전트는 일정을 구성하고 서버는 실제 장소·경로를 검증한다. 검증에 성공한 작업에만 저장 가능한 초안을 발급한다. [기존 API 계약](../specs/04-api.md)

## 여행 밀도와 식사 배치

서버는 이 명세의 일정 생성 규칙과 요청 날짜별 식사·관광 자리 순서를 에이전트 시스템 프롬프트에 넣는다. 최초 생성과 방문지 교체에 같은 규칙을 적용한다.

여행 밀도는 음식점을 제외한 하루 방문지 수다. 여유롭게는 2곳, 알차게는 3곳, 빼곡하게는 4곳을 배치한다. 음식점은 별도로 첫날과 마지막 날에 각각 2곳, 그 사이의 날에는 매일 3곳을 배치한다. 당일치기는 2곳이다. 따라서 알차게 선택한 3박 4일 일정은 관광·활동 방문지가 매일 3곳이고 음식점은 날짜순으로 2·3·3·2곳이다. 후보는 이 개수에 맞춰 요청한다. 휴무나 시간 충돌을 해결할 수 없는 자리는 자유 식사·관광으로 남긴다.

다음 표는 도착일과 출발일 사이에 온전히 여행하는 날에 적용한다. 3박 4일이면 2·3일차가 해당한다. 시작 시각은 여행지 현지 시각이며, 첫 일정인 아침 식사의 시작을 뜻한다.

| 여행 밀도 | 시작 시각 | 식사와 방문 순서 |
|---|---|---|
| 여유롭게 | 09:00 | 아침 → 오전 1곳 → 점심 → 오후 1곳 → 저녁 식사로 종료 |
| 알차게 | 08:00 | 아침 → 오전 1곳 → 점심 → 오후 1곳 → 저녁 식사 → 저녁 1곳 |
| 빼곡하게 | 08:00 | 아침 → 오전 1~2곳 → 점심 → 오후 1~2곳 → 저녁 식사 → 저녁 1~2곳 |

빼곡하게는 오전·오후·저녁 중 한 시간대에만 2곳을 배치해 하루 방문지를 정확히 4곳으로 맞춘다. 어느 시간대에 2곳을 배치할지는 영업시간과 이동시간을 고려해 정한다.

## 방문 후보 조회와 일정 검증

1. **후보 선택.** 서버는 여행 밀도와 일차별 식사 수로 자리를 정하고 중간 날의 첫 식사 시각을 고정한다. 첫 모델 호출은 각 자리에 취향에 맞고 서로 도보로 가까운 장소명과 같은 용도의 인근 대안 한 곳을 채운다.
2. **영업시간·도보 조회와 시간 배치.** 서버가 Google Places에서 날짜에 적용되는 영업 구간을 구하고 임시 순서의 인접 장소 간 도보 시간을 조회한다. 날짜별 특별 영업시간·휴무를 우선하고, 제공 범위를 벗어난 여행일에는 정규 요일 영업시간을 사용한다. 두 번째 모델 호출은 이 자료를 보고 같은 날의 관광 순서와 현지 방문·체류 시각을 정한다. [Google Places 영업시간](https://developers.google.com/maps/documentation/places/web-service/reference/rest/v1/places#Place)
3. **영업시간 미확인.** 장소가 확인됐지만 영업시간을 알 수 없으면 식당·실내 시설·야외 장소 모두 제안 시각으로 배치할 수 있다. 결과·저장 일정·공개 게시물에서 해당 장소에 ‘영업시간 확인 필요’를 표시한다.
4. **휴무와 시간 충돌.** 서버는 알려진 영업 구간과 도보 시간에 맞춰 방문 시각과 같은 날의 관광 순서를 조정한다. 필요하면 첫 모델 응답에 있는 인근 대안을 전체 여행에서 한 번 조회한다. 서버가 바뀐 구간의 이동시간과 방문 시각을 다시 맞춘다. 휴무나 시간 충돌을 해결할 수 없는 자리는 자유 식사·관광으로 남기고 실제 방문지끼리 다시 연결한다. 자유 일정에는 장소 ID·지도 링크·가상의 이동시간을 부여하지 않는다.
5. **초안 발급.** 실제 방문지가 남고 각 방문지와 연결 경로를 확인하면 자유 일정이 포함된 초안도 저장할 수 있다. 여행 전체가 자유 일정이거나 필수 장소·경로 조회 자체가 실패하면 작업은 `failed`로 종료한다. 실패 기록에는 단계·해당 일차·자리·사유를 남기고 진행률은 실행 중 메모리에만 둔다.
6. 생성과 부분 교체는 계정의 하루 5건·월 20건 중 1건으로 계산한다. 후보와 시각 배치에 필요한 두 번의 모델 호출을 예산에 예약한다. 기존 후보를 교체할 때는 추가 모델 호출 없이 장소·경로를 다시 조회한다.

최초 생성은 도보 기준이다. 결과 화면의 구간 버튼을 누르면 기존 대화상자에서 도보·대중교통·자동차를 모두 보여 준다. 사용자가 선택한 수단과 해당 수단의 예상 시간·거리를 두 방문지 사이 버튼에 표시한다. 서버는 실제 조회값을 사용한다. 생성·검증·구간 변경 오류는 입력과 이전 결과를 보존하고 화면 안에 한국어로 안내한다. [오류 안내](08-error-alerts.md)

구간 대화상자에는 세 수단을 항상 표시한다. 조회에 성공했으나 경로가 없으면 해당 수단을 ‘이 구간은 경로 없음’으로 표시하고 선택을 비활성화한다. 일시적 조회 실패에는 ‘다시 조회’를 제공한다. 수단 변경 시 기존 방문 종료와 다음 방문 시작 사이에 도착할 수 있을 때만 선택을 적용한다. 시간이 부족하면 기존 선택과 시각을 유지한다. 사용자가 저장한 일정에는 구간별 선택 수단을 보존한다.

### 저장 일정 재열람 비용

**Google을 유지하면 장소마다 `place_id`를 장기 저장하고, 일정을 다시 열 때 그 ID로 장소명과 좌표를 조회하는 방식입니다.**

Google을 유지한다. 새 일정에는 방문 항목 ID, Google 장소 ID, 여행일·방문 순서·예정 시각, 구간별 선택 수단을 장기 보관한다. Google에서 받은 방문지명·좌표·경로 시간·거리를 공개 게시 사본까지 포함한 영구 스냅샷으로 저장하지 않는다. Google Places 좌표는 최대 30일 임시 보관이 가능하지만 첫 구현은 장기 DB에 좌표를 넣지 않고 필요한 날의 장소 ID로 조회한다. [Places 정책](https://developers.google.com/maps/documentation/places/web-service/policies) · [서비스별 약관 §14.3](https://cloud.google.com/maps-platform/terms/maps-service-terms)

저장 상세에서는 OpenAI를 호출하지 않는다. 처음에는 선택한 날짜의 방문지만 Places Details로 조회하고, 같은 화면에서 받은 장소명과 좌표를 목록과 지도 핀이 공유한다. 핀 번호는 저장한 방문 순서를 쓴다. 날짜 전환 때 지도 인스턴스를 재사용하고, 선택한 수단의 시간·거리는 Routes에서 조회한다. 다른 두 수단은 구간 대화상자를 열 때 조회한다. 조회 당시 결과는 저장 당시와 달라질 수 있다.

#### 공개 게시물 표시와 조회 비용

공개 게시물 상세는 날짜별 방문 목록에 방문 순서·장소명·방문 시각을 표시한다. 장소명은 일정의 방문 라벨을 사용한다. 방문지 사이에는 선택한 이동수단만 표시한다. 장소별 ‘구글맵’ 링크를 누르면 해당 장소가 Google Maps에서 새 탭으로 열린다.

공개 목록과 상세는 Tripick DB에서 읽고, 날짜 탭 전환은 이미 받은 방문 목록을 필터링한다. 이 과정에서 Google 지도·장소·경로 API 호출은 0회이며 **Tripick의 Google 조회 비용은 0원**이다. 아래 재열람 비용 예시는 개인 저장 일정 상세에 적용한다.

## 일정 생성 모델


마지막 요약 화면에서 사용자가 GPT-6 Luna(`gpt-6-luna`, 기본값) 또는 GPT-6.1 Terra(`gpt-6.1-terra`)를 선택한 뒤 **AI 일정 생성**을 누른다. 프런트엔드는 여행 조건과 모델 ID를 `POST /api/generations`로 보내고 작업 상태를 조회한다. 검증에 성공하면 반환된 초안을 열고, 실패하면 해당 사유에 맞는 한국어 안내를 표시한다.

생성 중에는 같은 작업 ID를 2초 간격으로 조회한다. 생성 버튼 아래에 현재 단계와 진행률을 표시하고 일차별 확인 중에는 해당 일차도 함께 표시한다. 진행률은 후보 구성과 시각 조정 각 1단계, 여행 일차별 영업시간·경로 확인과 최종 검증 각 1단계를 기준으로 계산한다. 방문지 교체로 반복한 단계는 한 번만 집계한다. 서버가 검증된 초안을 확정하면 100%를 표시하고 결과 화면을 연다.

단계·일차·퍼센트는 실행 중인 서버 프로세스의 메모리에만 두고 작업 종료 시 지운다. 다른 서버 프로세스가 상태 조회를 받으면 브라우저는 마지막으로 받은 진행률을 유지한다. 아직 진행률을 받기 전에는 생성 중이라고 표시한다.

서버는 두 모델 ID만 허용하며 생략 시 Luna를 사용한다. 작업 접수 때 확정한 ID를 예산 예약, 캐시 키와 에이전트 실행에 사용한다. [Agents SDK 실행 설정](https://openai.github.io/openai-agents-python/ref/run_config/#agents.run_config.RunConfig.model)

후속 작업에서는 OpenRouter를 통해 여러 제공업체의 모델을 추가한다. 백엔드가 사용자에게 공개할 모델 목록과 제공업체별 모델 ID·단가 매핑을 관리하고, OpenRouter 키는 서버에서만 사용한다.

## 백엔드 요청 처리

모든 로그인 계정에 같은 정책을 적용한다. 아래 수치는 월 활성 사용자 50명을 가정한 초기 제안이다.

1. 생성 라우트에 사용자당 분당 3회, IP당 분당 30회를 적용한다. 캐시 요청도 포함한다. IP는 신뢰하는 프록시가 확인한 주소를 사용한다. 초과 시 429와 재시도 가능 시간을 반환한다.
2. 요청 본문은 최대 16 KiB로 제한하고 초과 시 413을 반환한다. 기존 조건 스키마와 서버 옵션을 검증하고, 파일이나 임의 프롬프트를 받지 않는다. 서버 지시문과 장소 자료까지 포함한 최종 입력에도 모델별 토큰 상한을 적용한다.
3. 계정·Idempotency-Key가 같은 재시도는 기존 작업에 연결하고 본문이 다르면 409를 반환한다. 동일 계정의 정규화한 조건·원본 일정 버전·모델·프롬프트 버전이 같고 장소 검증 자료가 아직 유효하면 캐시한 성공 결과를 반환한다. 다른 계정의 결과는 반환하지 않는다.
4. 새 실행은 계정당 동시 1건, 하루 5건, 월 20건을 제안한다. 모든 서버 인스턴스가 공유하는 DB에서 계정 한도와 전체 월 잔액을 한 트랜잭션으로 확인·예약한다. 일·월 경계는 한국 시간 기준이다. 캐시 적중에는 생성 횟수와 비용을 차감하지 않는다.
5. 모델, 입력·출력 토큰, 실행 턴, 도구 호출, 재시도 횟수를 서버 설정으로 제한한다. 허용된 최악의 실행 비용까지 예약할 수 있을 때만 외부로 요청한다. 성공·실패 모두 실제 사용량으로 정산하며 타임아웃으로 과금 여부가 불명확하면 예약을 유지하고 대조한다. 한도 저장소 장애 시 신규 실행을 차단한다.

## 월 예산 제안

OpenAI 호출 예산은 월 5만 원으로 시작하고 4만 원에 운영자에게 알린다. 50명이 월 20건씩 생성하면 월 1,000건이다. 예산 5만 원이면 건당 평균 50원, 20만 원이면 200원까지 감당한다. 모델 단가·환율·세금 여유분을 예약 단가에 반영한다. 장소·경로 공급자와 호스팅 요금은 별도로 집계한다.

첫 달에는 생성 건수, 실제 토큰과 비용, 캐시 적중, 한도 차단 건수를 기록한다. 7일 일정과 짧은 일정을 나누어 건당 비용을 비교한 뒤 상향 여부를 정한다.

## 인수 기준

- 인증·CSRF·입력 검증 실패 및 한도 초과 시 유료 호출은 0건이다.
- 동시 요청이 마지막 예산이나 계정 한도를 경합해도 허용량만 실행된다. 같은 요청을 재전송해도 두 번 결제되지 않도록 외부 호출 횟수로 검증한다.
- 예산 소진 후에도 본인에게 유효한 캐시 결과는 조회할 수 있다. 타 계정 요청 또는 검증 유효기간이 지난 결과는 캐시에서 반환하지 않는다.
- 실제 장소와 경로를 확인하지 못한 일정은 저장할 수 없다.
- 방문 시각 확정 전에 임시 순서의 구간별 이동시간이 에이전트에 전달된다. 최종 출발 시각이 달라진 구간은 해당 시각으로 재조회한 결과를 사용한다.
- 특별 영업시간이 없으면 정규 요일 시간을 사용한다. 둘 다 알 수 없는 장소도 일정에 포함하고 ‘영업시간 확인 필요’를 표시한다. 휴무가 확인된 장소는 방문 목록에서 제외한다.
- 호텔·예약 입력이 없는 요청에서는 임의의 숙소 출발점이나 예약 시각을 만들지 않는다. 조회된 입장 마감이나 폐관 시각은 지켜야 한다.
- 자동 교체 후에도 휴무나 시간 충돌이 남으면 해당 자리만 자유 일정으로 남긴다. 나머지 방문지 간의 새 경로와 시각을 확인하고 저장·게시할 수 있어야 한다.
