# 02 · 목표 구조와 결정 기록

> 2026-11-16 최종 결정: Supabase Auth를 유지하고 OAuth 시작·코드 교환·토큰 관리를 FastAPI BFF로 이전한다. [ADR 0005](../adr/0005-supabase-bff.md)를 따른다. 홈 세계지도 포함, 닉네임 대소문자 구분, 목록 10개, 비용 설정과 현재 구현 상태는 [06 구현·운영](06-implementation.md)을 따른다.
## 목표 데이터 흐름

```text
React → FastAPI 로그인 시작 → Supabase Auth(Google·Kakao)
Supabase → FastAPI 콜백 → 서버 PKCE 코드 교환·암호화 보관
      ← HttpOnly 세션 쿠키 ← 서버 세션·사용자 저장 ← PostgreSQL
React → FastAPI(세션·입력·소유권·저장 한도 검증) → PostgreSQL
      ← 서버 결과 ← 조회·저장·편집·삭제·게시·하트
React → Google Maps JavaScript API: 모든 결과 여행지의 지도 바탕 표시
홈 세계지도 → 별도 SVG 시각화(React Simple Maps 추천)
후속: FastAPI → OpenAI SDK 및 장소·경로 제공자 → 검증된 일정 → 마커·방문 순서·실제 경로
```

현재 BFF 인증·서버 일정·커뮤니티 API를 연결했다. 실제 생성·장소·경로 검증은 후속 구조다. 일정·게시·하트·인증 토큰은 localStorage에 저장하지 않으며, 프런트엔드에서 업무 DB에 직접 접근하지 않는다. Google Maps의 브라우저 렌더링 호출은 저장 API 흐름과 별개다. OpenAI SDK의 구체 모델·Agents SDK 사용 여부는 아직 결정하지 않는다.

## 확정된 제품 규칙

- Google·Kakao 로그인, 계정별 소유권, 활성 저장 일정 최대 3개.
- 생성·재생성·저장 전 결과는 저장 슬롯을 쓰지 않는다. 단, 활성 저장 일정이 이미 3개이면 신규 생성과 미저장 결과의 재생성을 차단하고 본인 소유의 기존 저장 일정 재생성만 허용한다. 재생성은 원본을 즉시 덮어쓰지 않으며, 사용자가 검증된 결과를 확인하고 같은 일정 ID에 재저장한다. 생성 실패·취소·버전 충돌 시 원본을 보존한다. 같은 저장 일정을 수정해 재저장해도 개수는 늘지 않고, 전체 삭제 성공 후에만 슬롯이 돌아온다.
- 사용자가 결과를 확인하고 명시적으로 저장한다. 저장 전 결과를 자동으로 저장 일정으로 취급하지 않는다.
- 2026-11-04: 현재 구현과 MVP 목표를 분리해 문서화하고, 실제 사용자 간 커뮤니티를 MVP에 포함하며, 인증은 Supabase Auth를 확장한다.
- 2026-11-15: Supabase Auth는 로그인 제공자로 유지하되 FastAPI가 인증 토큰·사용자 ID와 서버 세션을 관리한다. 브라우저는 HttpOnly 쿠키의 불투명 세션 식별자로 API를 호출한다. 이는 2026-11-05의 브라우저 세션 유지 결정을 대체한다. [새 결정](../adr/0002-server-session.md), [이전 결정](../adr/0001-supabase-auth-fastapi-domain.md).
- 게시 일정은 비로그인 방문자도 읽을 수 있다. 게시·게시 취소·하트는 로그인 사용자만 한다.
- 게시 시 저장 일정의 사본을 만든다. 개인 일정 수정은 게시물에 자동 반영하지 않는다. 원본 저장 일정을 전체 삭제하면 연결된 게시물과 하트도 삭제한다.
- 작성자는 사용자가 정한 공개 닉네임으로 표시한다. 계정 ID·이메일·제공자 프로필 이름을 작성자 표시로 사용하지 않는다.
- 본인 게시물에도 하트를 허용한다. 게시 취소 후 재게시하면 하트는 0개, 게시 시각은 새로 시작한다.
- 게시 버튼 한 번으로 즉시 공개한다. 공개 전 별도 확인 화면은 만들지 않는다.
- 공개 사본에는 여행지·일수·테마·방문 장소와 방문 순서만 넣는다. 정확한 여행 날짜와 개인 조건은 제외한다.
- 공개 닉네임은 사용자 간 중복을 허용하지 않는다. 닉네임을 바꾸면 기존 게시물에도 새 닉네임을 표시한다. 게시물의 공개 표시 이름은 작성자의 현재 닉네임을 따른다.
- 공개 닉네임은 첫 게시 전에 정한다. 이후 변경을 허용하되 다른 계정이 사용 중인 이름으로는 바꿀 수 없다.
- Supabase가 확인된 동일 이메일의 Google·Kakao 신원을 연결하면 Supabase 사용자 ID 하나를 Tripick 계정 하나로 사용한다. Kakao가 이메일을 제공하지 않으면 별도 계정이 만들어질 수 있다. 이메일은 서비스 계정 키로 사용하지 않는다.
- 커뮤니티 목록은 하트 수 내림차순, 게시 시각 오름차순, 게시물 ID 오름차순으로 정렬한다.
- 기존 브라우저 `localStorage`의 모의 개인 일정·게시물은 서버 저장소로 자동 이전하지 않는다. 전환 전에 이 차이를 사용자에게 알린다.
- 2026-11-15: 홈 세계지도를 제외한 모든 결과·저장·게시 일정 지도는 Google Maps로 통일한다. 국내 지도 3종 선택을 대체하고 선택 UI·API 허용값도 함께 정리한다. Google Maps 바탕 표시를 먼저 구현하고, 일정 장소 마커·방문 순서·실제 경로는 OpenAI SDK 연결 후 진행한다.
- 2026-11-06: 일정 생성에는 시작일·종료일을 필수로 받는다. 예산은 PRD F01의 필수 조건과 달리 이번 MVP에서 제외한다. 인원은 2026-11-15 결정으로 `1·2·3·4·5명 이상` 구간으로 받는다. API 값은 `1`, `2`, `3`, `4`, `5_plus`이며 1~4는 정확한 인원, 5_plus는 5명 이상이다. 이동수단은 도보·대중교통·자차만 허용한다. 생성은 작업 ID와 상태 조회를 사용하는 비동기 API다.
- 선택한 이동수단 하나를 일정 전체의 인접 장소 구간에 적용한다. 각 구간은 실제 경로 API에서 조회한 경로 거리와 예상 이동시간을 표시한다. 직선거리나 거리 ÷ 고정 속도로 이동시간을 대체하지 않는다. 대중교통의 배차·환승·대기 및 자차 교통상황 반영 여부는 제공자 응답·조회 조건을 따르며 실제 도착시간을 보장하지 않는다. 자차는 경로·예상 시간만 다루고 렌터카 예약·주차·통행료는 제외한다. `5명 이상`을 정확히 5명으로 간주하거나 인원별 비용·좌석을 보증하지 않는다.
- 여행 기간은 시작일·종료일 포함 최대 7일이다. 공개 닉네임은 2~20자의 한글·영문·숫자만 허용한다. 앞뒤·중간 공백, 탭·줄바꿈 등 공백 문자가 있으면 자동 제거하지 않고 입력 오류로 거부한다.
- 여행지는 도시·섬·지역을 모두 가리키는 용어다. 현재 프런트엔드의 선택 목록만 MVP에서 허용하고 한 일정에 여행지 하나만 담는다. 자유 검색·다중 여행지는 후속 범위다.

## 지도 구현 경계

- `GoogleSeoulMap.tsx`의 로더·오류 표시를 재사용해 여행지 중심 좌표·확대 수준을 입력받는 공통 지도로 확장한다. 서울 조건문을 제거하고 결과·저장 상세·게시 상세의 지도 표시 지점에 적용한다.
- 여행지 중심 좌표는 서버의 허용 여행지 목록에 검토된 값으로 둔다. 지도 바탕을 위한 중심점이며 일정 장소의 좌표나 실제 경로 근거로 사용하지 않는다. 좌표 누락·지도 로드 실패 시 안내하고 서울이나 모의 경로로 대체하지 않는다.
- 홈은 Google Maps API에서 제외한다. React Simple Maps와 검토된 GeoJSON/TopoJSON으로 SVG 세계지도를 구성하는 방식을 추천한다. 국가 선택과 색상 표현에 적합하다. 도입 전 React 19 호환성·지도 데이터 라이선스·키보드 접근성을 확인한다. 지금 라이브러리를 설치했다는 뜻은 아니다. [공식 문서](https://www.react-simple-maps.io/docs/getting-started)
- 브라우저 Maps JavaScript API 키는 공개되는 키이므로 웹사이트·API 제한을 적용한다. 서버 장소·경로 조회 키와 OpenAI 키는 별도 비밀 설정이다. [Google 키 제한](https://developers.google.com/maps/documentation/javascript/get-api-key)
- OpenAI SDK는 AI 생성 연결용이다. SDK 연결만으로 실제 장소·경로가 검증되지 않으며, 후속 단계에서 장소·영업시간·경로 제공자의 응답과 연결해야 한다.

## DB·Alembic 반영 계획

기존 `0001_users`를 수정하지 않고 후속 리비전을 추가한다. 다음은 추가 대상이며 현재 존재하는 테이블 목록이 아니다. SQLAlchemy 메타데이터와 Alembic DDL을 함께 갱신한다.

| 테이블·변경 | 관계·제약 | 적용 단계 |
|---|---|---|
| `users` 공개 닉네임 필드 | 선택 필드로 추가 후 검증된 값만 저장, 중복 방지 unique. 기존 사용자 보존 | 서버 저장 전환 |
| `auth_sessions` | `users.id` FK, 세션 해시 unique, 만료·폐기 시각, 서버 토큰 암호화. 계정당 여러 기기 허용 | 서버 인증 전환 |
| OAuth 트랜잭션 | state·브라우저 쿠키의 해시, 암호화한 PKCE verifier, 만료·소비 시각. 소비 시 verifier 삭제 | ADR 0005, `oauth_transactions` |
| `trips` | 소유자 FK, 서버 ID, 내용·버전·생성/수정 시각. 활성 최대 3개는 사용자 행 잠금과 같은 트랜잭션으로 보장 | 서버 저장 전환 |
| `posts` | 원본 일정 FK unique, 공개 허용 필드만 담은 사본. 원본 삭제 시 cascade | 커뮤니티 전환 |
| `post_hearts` | 게시물·사용자 FK, `(post_id, user_id)` unique. 게시물 삭제 시 cascade | 커뮤니티 전환 |
| `idempotency_keys` | 사용자·요청 범위·키 unique, 본문 해시·결과 참조·만료. 변경과 같은 트랜잭션으로 기록 | 재시도 가능한 쓰기 API |
| `generations`, `drafts`, `edit_drafts` | 소유자·작업 상태·조회 근거·원본 버전·만료. 재생성 결과에는 대상 저장 일정 참조와 기준 버전을 결합하며 다른 일정·신규 저장에 재사용 금지. 저장 일정 슬롯과 분리 | OpenAI SDK 연결 단계 |

현재 계약은 일정 전체 삭제를 사용한다. 삭제한 일정을 별도 활성 상태로 남기는 기능을 임의로 추가하지 않는다. 재저장 충돌은 버전으로 검사한다. 공개 사본에 원본 JSON 전체를 복사하지 않는다. 장소·경로 원본 데이터의 저장 필드는 제공자 약관 검증 후 확정한다.
