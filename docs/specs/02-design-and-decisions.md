# 02 · 목표 구조와 결정 기록

## 목표 데이터 흐름

```text
React 조건 선택 → Supabase Auth 로그인(브라우저 세션) → FastAPI 토큰 검증·사용자 저장
                         → 장소/영업시간/경로 조회 → 일정 생성·검증
                         → 결과 확인 → 명시적 저장 → PostgreSQL
저장 일정 → 편집·재저장·삭제
저장 일정 → 게시 사본 → 공개 목록·하트
```

사용자 저장 API만 프런트엔드와 백엔드에 연결됐다. 일정·게시·하트와 생성·지도 흐름은 목표다. OpenAI Agents SDK, Google Maps 등의 구체 호출·요금·약관·지원 범위는 대표 지역 실측 후 확정한다.

## 확정된 제품 규칙

- Google·Kakao 로그인, 계정별 소유권, 활성 저장 일정 최대 3개.
- 생성·재생성·저장 전 결과는 저장 슬롯을 쓰지 않는다. 같은 저장 일정을 수정해 재저장해도 개수는 늘지 않고, 전체 삭제 성공 후에만 슬롯이 돌아온다.
- 사용자가 결과를 확인하고 명시적으로 저장한다. 저장 전 결과를 자동으로 저장 일정으로 취급하지 않는다.
- 2026-11-04: 현재 구현과 MVP 목표를 분리해 문서화하고, 실제 사용자 간 커뮤니티를 MVP에 포함하며, 인증은 Supabase Auth를 확장한다.
- 2026-11-05: Supabase Auth와 브라우저 세션을 유지한다. FastAPI는 Supabase Auth에 토큰을 검증해 사용자 행을 PostgreSQL에 저장한다. 별도 백엔드 세션은 만들지 않는다. 향후 개인 일정·게시·하트의 권한 검사와 저장도 FastAPI가 맡는다. [결정 이유](../adr/0001-supabase-auth-fastapi-domain.md).
- 게시 일정은 비로그인 방문자도 읽을 수 있다. 게시·게시 취소·하트는 로그인 사용자만 한다.
- 게시 시 저장 일정의 사본을 만든다. 개인 일정 수정은 게시물에 자동 반영하지 않는다. 원본 저장 일정을 전체 삭제하면 연결된 게시물과 하트도 삭제한다.
- 작성자는 사용자가 정한 공개 닉네임으로 표시한다. 계정 ID·이메일·제공자 프로필 이름을 작성자 표시로 사용하지 않는다.
- 본인 게시물에도 하트를 허용한다. 게시 취소 후 재게시하면 하트는 0개, 게시 시각은 새로 시작한다.
- 게시 버튼 한 번으로 즉시 공개한다. 공개 전 별도 확인 화면은 만들지 않는다.
- 공개 사본에는 여행지·일수·테마·방문 장소와 방문 순서만 넣는다. 정확한 여행 날짜와 개인 조건은 제외한다.
- 공개 닉네임은 사용자 간 중복을 허용하지 않는다. 닉네임을 바꾸면 기존 게시물에도 새 닉네임을 표시한다. 게시물의 공개 표시 이름은 작성자의 현재 닉네임을 따른다.
- 공개 닉네임은 첫 게시 전에 정한다. 이후 변경을 허용하되 다른 계정이 사용 중인 이름으로는 바꿀 수 없다.
- Supabase가 확인된 동일 이메일의 Google·Kakao 신원을 연결하면 Supabase 사용자 ID 하나를 Tripick 계정 하나로 사용한다. Kakao가 이메일을 제공하지 않으면 별도 계정이 만들어질 수 있다. 이메일은 서비스 계정 키로 사용하지 않는다.
- 커뮤니티 목록은 하트 수 내림차순, 게시 시각 오름차순, 게시물 ID 오름차순으로 정렬한다.
- 기존 브라우저 `localStorage`의 모의 개인 일정·게시물은 서버 저장소로 자동 이전하지 않는다. 전환 전에 이 차이를 사용자에게 알린다.
- 1차 지도 검증은 Google Maps로 시작하되 MVP 완료 기준에는 국내 네이버지도·카카오맵·Google Maps 선택과 해외 Google Maps를 유지한다.
- 2026-11-06: 일정 생성에는 시작일·종료일을 필수로 받는다. 예산은 PRD F01의 필수 조건과 달리 이번 MVP에서 제외한다. 인원은 정확한 숫자 대신 `1·2·3·4명 이상` 구간으로 받는다. 이동수단은 도보·대중교통·자동차를 선택한다. 생성은 작업 ID와 상태 조회를 사용하는 비동기 API다.
- 선택한 이동수단 하나를 일정 전체의 인접 장소 구간에 적용한다. 자동차는 경로·예상 시간만 다루고 렌터카 예약·주차·통행료는 제외한다. `4명 이상`을 정확히 4명으로 간주하거나 인원별 비용·좌석을 보증하지 않는다.
- 여행 기간은 시작일·종료일 포함 최대 14일이다. 요청한 수단의 경로를 실제로 확인하지 못하면 자동 대체하지 않고 이유를 보여주며 확정 저장을 막는다. 공개 닉네임은 앞뒤 공백 제거 후 2~20자, 한글·영문·숫자·단어 사이 공백을 허용한다.
- 여행지는 도시·섬·지역을 모두 가리키는 용어다. 현재 프런트엔드의 선택 목록만 MVP에서 허용하고 한 일정에 여행지 하나만 담는다. 자유 검색·다중 여행지는 후속 범위다.

## 제안 중인 데이터 경계

| 개념 | 필요한 관계·제약 | 상태 |
|---|---|---|
| 사용자 신원 | Supabase Auth 사용자 ID를 `users.id`로 사용. 이메일은 선택 정보. `PUT /api/users/me`가 Supabase Auth에서 토큰을 확인하고 행을 생성·갱신 | Google 경로 구현, Kakao 로그인 UI·실제 연동 미구현 |
| 생성 결과 | 조건·조회 근거·검증 상태와 함께 보관하고 저장 일정과 구분 | PRD 제안 |
| 저장 일정 | 소유자, 일정 내용, 버전, 활성 상태. 소유자별 활성 최대 3개를 원자적으로 보장 | PRD 목표 |
| 편집 작업본 | 원본 버전과 변경 내용을 분리하고 충돌 시 원본 보존 | PRD 제안 |
| 게시 일정 | 여행지·일수·테마·장소·순서의 공개 사본과 작성자 참조. 원본 전체 삭제 시 함께 삭제 | 제품 규칙 확정, 필드 설계 필요 |
| 하트 | 사용자·게시 일정 조합이 유일 | 실제 공유 목표에 필요한 제약 |
| 공개 닉네임 | 사용자 간 고유하며 작성자의 현재 표시 이름으로 참조 | 제품 규칙 확정, 형식 검증 설계 필요 |

현재 구현된 업무 API는 `PUT /api/users/me`뿐이고, 별도로 `GET /health`가 있다. `PUT`은 `Authorization: Bearer <Supabase access token>`으로 호출하며 본문은 없다. 응답은 `id`와 nullable `email`이고, 토큰 오류 401·미지원 제공자 403·인증 서비스 오류 502·DB 오류 503을 반환한다. `users`는 Supabase 사용자 ID(UUID)를 기본 키로, 이메일을 선택 필드로 둔다. 앞으로의 요청·응답 설계안은 [API·JSON 계약](04-api.md)에 있다. 기존 `Tripick_03_API_데이터계약.md`의 FastAPI 자체 OAuth 경로와 일정 API는 이전 초안이다.

## 결정이 필요한 항목

| ID | 질문 | 영향 |
|---|---|---|
| D-C04 | 닉네임 중복 비교의 세부 정규화와 변경 UI | 프로필·게시물 표시 |
| D-C05 | 공개 장소의 주소·좌표·지도 연결에 필요한 최소 필드 | 지도 표시·제공자 약관 |
| D-C07 | 커뮤니티 목록 페이지네이션 크기 | 공개 목록 |
| D-A01 | Kakao 제공자 설정·로그인 버튼·실제 로그인 검증. 공통 사용자 API와 nullable 이메일은 준비됨 | 로그인·계정 복원 |
| D-M01 | 지도·장소·영업시간·경로의 지역·수단별 지원 및 약관 | 생성·지도 완료 기준 |
| D-P01 | 선택 여행지별 외부 조회 지원, 생성 비용 한도, 저장 실패 정책 | 입력·요금·검증 |

확정되지 않은 항목은 구현 시 임의의 기본값으로 승격하지 않는다. Tripick은 이메일을 계정 키로 쓰지 않으며 Supabase Auth가 연결한 사용자 ID를 따른다.
